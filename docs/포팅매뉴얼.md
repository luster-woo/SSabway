## 0. 시스템 구성 개요

```
브라우저 ──HTTPS(443)──▶ OpenVidu 자체 nginx (host 네트워크, Let's Encrypt, ssabway.site)  ── /opt/openvidu, 5번 참고
                              │
                              ├─ OpenVidu 경로(대시보드·REST API·/recordings/**) → openvidu-server / kms / coturn
                              │
                              └─ 그 외 전부 ──HTTP──▶ 127.0.0.1:5442
                                                          │
                                                    ┌────────────┐
                                                    │   nginx    │  (이 저장소, deploy/nginx.conf)
                                                    │ (reverse   │
                                                    │  proxy)    │
                                                    └─────┬──────┘
                                  ┌───────────────────────┼────────────────┬───────────────┐
                                  ▼                       ▼                ▼               ▼
                            frontend(nginx)          api(Spring)     signaling(Spring)   ai(FastAPI)
                            정적 SPA 서빙               :8080           webrtc :8080         :8000
                                                          │                   │                │
                                                          ├── mysql:3306 ─────┘                │
                                                          ├── redis:6379                       │
                                                          │                   │                │
                                                          └── ODsay / GMS / S3 / Azure Speech (외부 SaaS)
                                                                              │
                                                                     (signaling → https://ssabway.site 로 재진입,
                                                                      OpenVidu 세션 발급 — 5-5 참고)
```

> OpenVidu는 외부 SaaS가 아니라 **같은 EC2 서버(`/opt/openvidu`)에 OpenVidu CE On-Premises로 별도 구동 중**이며, **TLS 종단과 `ssabway.site` 도메인의 실제 진입점 역할을 OpenVidu 자체 nginx가 담당**한다(작성자 확인 완료). 이 저장소의 nginx(`deploy/nginx.conf`)는 그 뒤에서 평문 HTTP만 받는다. `edge` 도커 네트워크는 이 공인 트래픽 경로와 무관하며, 이 저장소 nginx ↔ Jenkins 컨테이너 간 내부 통신(웹훅 라우팅)용으로 보인다. 상세는 5번 참고.

- **frontend** : Vite + React 19 SPA, nginx(alpine)로 정적 서빙 (사용자 PWA + 관리자 웹을 라우트로 분리)
- **api (`backend/ssabway`)** : 회원/인증, 경로 안내, 역 내 길찾기, 상담 생성, 역무원 기능(로그인/대기열/블랙리스트), 표지판 인식 AI 연동
- **signaling (`backend/ssabway_webrtc`)** : 화상 상담 세션(OpenVidu) 생성·조회·취소·종료, 녹취 S3 업로드, OpenVidu 웹훅 수신
- **ai (`ai/serve`)** : 표지판 인식(YOLO+ResNet18, FastAPI), 얼굴 좌표 검출(WS, 화상 상담 모자이크용), 실시간 번역 자막(Azure Speech)
- **mysql 8.0.46**, **redis 7** : 공용 데이터/토큰 저장소
- **nginx(deploy/nginx.conf)** : 위 4개 서비스 앞단 리버스 프록시 (경로 기반 라우팅)

### 3) 배포 시 특이사항

- **compose 파일 조합**
  - 로컬 개발: `docker-compose.yml` + `docker-compose.override.yml` (override는 자동 병합, 컨테이너 포트를 로컬호스트에 개별 노출)
  - 운영 배포: `docker-compose.yml` + `docker-compose.prod.yml` (override는 사용하지 않음 — `.dockerignore`/git상 로컬 전용)
    ```bash
    docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env up -d --build
    ```
  - `docker-compose.prod.yml`은 `ai` 서비스와 `nginx` 서비스, 그리고 외부 네트워크 `edge`(`external: true`)를 포함한다. **`edge`는 최상위 리버스프록시·Jenkins와 공유하는 네트워크**이며, 이 저장소의 compose가 직접 생성하지 않으므로 **사전에 `docker network create edge`로 만들어져 있어야 `nginx` 서비스가 기동된다.**
- **OpenVidu는 이 저장소의 compose에 포함되어 있지 않다.** 같은 EC2의 `/opt/openvidu`에 OpenVidu CE 2.32.2(On-Premises 공식 설치본)로 별도 구동 중이며, **OpenVidu 자체 nginx가 `ssabway.site`의 실제 인터넷 진입점**이다(TLS 종단 후 HTTP로 이 저장소 nginx에 리버스 프록시) — 상세 구성은 5번 참고.
- **AI 모델 가중치는 이미지에 포함되지 않는다.** 배포 서버의 `/opt/models`(prod) 또는 `./ai/serve/models`(local override)에 아래 파일을 직접 배치해야 `/predict`가 동작한다. (없어도 컨테이너는 뜨고 얼굴 검출·자막은 정상 동작, `/predict`만 503)
  ```
  models/detector.pt      YOLOv8n (6MB)
  models/classifier.pt    ResNet18 체크포인트 (45MB)
  ```
- **DB 초기화는 최초 1회만 자동 실행된다.** `deploy/db/schema.sql`이 MySQL 컨테이너의 `docker-entrypoint-initdb.d`에 마운트되어 **볼륨이 비어있을 때만** 실행된다. 이미 데이터가 있는 볼륨에는 반영되지 않으므로, 스키마 변경 시 수동 `ALTER TABLE` 또는 볼륨 재생성이 필요하다.
- **nginx 업스트림은 변수+resolver 방식**(`resolver 127.0.0.11`)을 사용한다. 컨테이너가 재생성되어 내부 IP가 바뀌면(예: OOM 재시작) DNS를 새로 조회하지만, 업스트림 컨테이너를 재배포한 뒤에는 **nginx도 함께 restart**해야 한다(`Jenkinsfile`의 `nginx 재시작` 스테이지 참고: `nginx -t && ... restart nginx`).
- **`/api/v1/consultations`의 라우팅이 두 백엔드로 분기**된다 (`deploy/nginx.conf` 참고). `nginx.conf` 자체를 수정한 경우 반드시 위 규칙(정확 일치 → 정규식 → 최장 prefix) 순서/내용을 유지해야 한다.
  - `POST /api/v1/consultations` (상담 생성) → `api`
  - `POST /api/v1/consultations/{id}/summary` (상담 요약) → `api`
  - 그 외 `/api/v1/consultations/{id}`, `/cancel` → `signaling`
  - `/api/v1/openvidu/**` (OpenVidu 커넥션·웹훅) → `signaling`
  - `/ws/v1/ai/**` (실시간 번역 자막 WebSocket) → `ai` (백엔드 미경유, 직결)
  - 그 외 `/api/**` → `api`
  - `/` → `frontend`
- **`client_max_body_size 20M`** (nginx) — 표지판 사진 업로드 한도. 백엔드(`multipart.max-file-size: 15MB`)보다 크게 유지해야 함.
- **AI 서버(8000)는 외부에 포트를 열지 않는다.** 보안그룹/방화벽에서 차단하고 도커 내부 네트워크로만 `api`, `nginx`가 접근하도록 구성 (`docker-compose.prod.yml`에는 `127.0.0.1:8000:8000`으로 로컬호스트에만 바인딩되어 있어 외부 접근은 실질적으로 차단됨).
- **메모리 요구사항**: Jenkins 배포 파이프라인은 가용 메모리 2,500MB 미만이면 빌드를 시작하지 않는다(OOM으로 인한 mysql 다운 방지). AI 워커 1개가 약 1GB를 상시 점유하므로, Spring 2개 + AI + MySQL/Redis가 같은 EC2에서 돈다면 **최소 4vCPU / 8GB 이상 권장**.
- **JVM 힙 옵션**: `-XX:MaxRAMPercentage=75`로 컨테이너 메모리 제한에 비례해 힙을 잡으므로, 배포 시 컨테이너별 메모리 제한(`mem_limit` 등)을 명시하는 것을 권장.
- **HTTPS 필수**: 카메라/WebRTC/Geolocation/서비스워커는 secure context에서만 동작한다. 운영 도메인은 `https://ssabway.site`이며, **TLS 종단은 이 저장소가 아니라 OpenVidu 자체 nginx(`/opt/openvidu`, Let's Encrypt)가 담당**한다. 본 저장소의 `deploy/nginx.conf`는 80 포트에서 평문 HTTP만 받고(`X-Forwarded-Proto https`는 앞단이 원래 HTTPS였음을 백엔드에 알려주기 위한 고정 헤더), OpenVidu nginx가 `127.0.0.1:5442`로 리버스 프록시해 준다 — 5번 참고. 채점 환경을 이 저장소만으로 재현하려면 별도의 TLS 종단 계층(OpenVidu 프록시 또는 그에 준하는 리버스 프록시)을 앞에 둬야 한다.
- **배포 자동화(Jenkins)**: `main` 브랜치 push/머지 시 `Jenkinsfile`이 `/home/ubuntu/app`에서 `git merge --ff-only origin/main` 후 변경된 경로에 따라 서비스별로 `docker compose up -d --build <service>`를 개별 실행한다(동시 빌드 금지, 메모리 절약). 채점 환경에서 CI 없이 수동 배포할 경우 위 "compose 조합" 항목의 명령을 그대로 사용하면 된다.

### 4) DB 접속 정보 및 주요 계정/프로퍼티 파일 목록

| 파일 | 역할 |
|---|---|
| `.env` (루트, git 미포함) | Docker Compose 전역 환경변수 — **DB 계정, 각종 외부 서비스 키 전부 여기서 관리** (템플릿: `.env.example`) |
| `backend/ssabway/src/main/resources/application.yml` | api 서비스 설정. `${...}` placeholder는 `.env`(Docker) 또는 `application-secret.yml`(로컬)에서 채워짐 |
| `backend/ssabway/src/main/resources/application-secret.yml.example` | 로컬 실행 전용 시크릿 템플릿 → 복사해 `application-secret.yml`로 사용 (gitignore 대상, Docker 실행 시 미사용) |
| `backend/ssabway_webrtc/src/main/resources/application.yaml` | signaling 서비스 설정 |
| `backend/ssabway_webrtc/src/main/resources/application-secret.example.yaml` | 위와 동일한 역할(signaling용) |
| `deploy/db/schema.sql` | DB 스키마 정의(DDL). 최초 1회만 자동 실행 |
| `deploy/nginx.conf` | 운영/로컬 공용 리버스 프록시 설정 |
| `frontend/public/config.js` | 프론트 런타임 환경설정(`window.__ENV__`) |

**DB 접속 정보(운영)**
- Docker 내부 네트워크 기준: `jdbc:mysql://mysql:3306/${MYSQL_DATABASE}`
- 계정: `root` / `${MYSQL_ROOT_PASSWORD}` (compose 상 root 계정을 그대로 사용 — 별도 애플리케이션 전용 계정 없음)
- 로컬에서 직접 접속: `docker-compose.override.yml` 기준 `localhost:3307` (root / .env의 `MYSQL_ROOT_PASSWORD`)

**주요 테이블(ERD 요약)**: `stations`(역), `users`(사용자), `staffs`(역무원, 역당 1계정), `points`/`edges`/`edge_translations`(역 내 길찾기 그래프+다국어 안내문), `blacklists`, `consultations`(api가 생성, signaling이 상태 전이). 상세 ERD는 `docs/erd.docx` 참고.

> ⚠️ 역무원(`staffs`) 로그인 계정과 역(`stations`)/포인트(`points`)/엣지(`edges`) 데이터는 `schema.sql`에 시드 데이터가 없다 — **4번 항목의 최신 DB 덤프에 포함된 데이터로 채워야 실제 로그인·길찾기 시연이 가능**하다.

## 3. DB 덤프 파일 최신본

- [ ] `deploy/db/schema.sql`(DDL)은 저장소에 포함되어 있으나, **역/포인트/엣지/역무원 계정 등 시연에 필요한 데이터(DML)는 별도 덤프 파일로 준비 필요**.
- [ ] 최신 덤프 파일을 `<파일명>.sql`로 제출 폴더(`exec`)에 포함할 것.
- [ ] 덤프 생성: `deploy/db/dump.sh` 스크립트 사용 (`mysql` 컨테이너 안에서 `mysqldump` 실행, 컨테이너에 이미 설정된 `MYSQL_ROOT_PASSWORD`/`MYSQL_DATABASE`를 그대로 사용하므로 비밀번호를 별도 입력할 필요 없음).

  ```bash
  # 로컬 (docker-compose.yml + override.yml)
  ./deploy/db/dump.sh

  # 운영 서버 (docker-compose.yml + prod.yml), /home/ubuntu/app 에서 실행
  ./deploy/db/dump.sh --prod

  # 출력 경로 직접 지정
  ./deploy/db/dump.sh --prod -o ssabway_dump_20260808.sql
  ```

  기본 출력 경로는 `deploy/db/dumps/ssabway_dump_YYYYMMDD_HHMMSS.sql`이며, 실제 데이터가 담긴 파일이라 `.gitignore`에 `deploy/db/dumps/`를 추가해 실수로 커밋되지 않도록 해 두었다 — 제출 시에는 이 파일을 `exec` 폴더로 직접 복사할 것.

## 5. 서버 내 OpenVidu 인프라

`/opt/openvidu`에 **OpenVidu Community Edition On-Premises 설치본**(공식 설치 스크립트로 배포)이 별도 스택으로 떠 있다. 이 저장소(`S15P11D104`)의 compose와는 완전히 분리되어 있고, 유일한 접점은 같은 EC2 호스트를 공유한다는 것뿐이다. `docker-compose.yml`은 "DO NOT MODIFY" 명시가 있는 OpenVidu 공식 파일이며, 실제 설정은 전부 `/opt/openvidu/.env`에서 관리된다.

### 5-1) 구성 요소

| 서비스 | 이미지 | 네트워크 | 역할 |
|---|---|---|---|
| `openvidu-server` | `openvidu/openvidu-server:2.32.2` | **host** | REST API(`SERVER_PORT=5443`, `SERVER_SSL_ENABLED=false` — TLS는 앞단 nginx가 처리), 세션/토큰 발급, 웹훅 발송 |
| `kms` | `kurento/kurento-media-server:7.3.0` | **host** | 실제 오디오/영상 미디어 처리. 미디어 포트 `KMS_MIN_PORT~KMS_MAX_PORT` = `40000~57000` |
| `coturn` | `openvidu/openvidu-coturn:2.32.2` | bridge (포트만 게시) | STUN/TURN, NAT 통과. `3478/tcp`, `3478/udp` 게시, 릴레이 포트는 `COTURN_MIN_PORT~MAX_PORT`(기본 `57001~65535`, `.env`에 미설정 시 기본값) |
| `nginx` | `openvidu/openvidu-proxy:2.32.2` | **host** | OpenVidu 대시보드/REST API/녹취 파일 서빙 + Let's Encrypt(`CERTIFICATE_TYPE=letsencrypt`, `DOMAIN_OR_PUBLIC_IP=ssabway.site`)로 TLS 직접 발급. `WITH_APP=true`로 커스텀 앱을 얹는 기능 지원(아래 5-2 참고) |
| `app` (선택) | `openvidu/openvidu-call:2.32.2` | host | OpenVidu 기본 데모 화상통화 앱. 정의 파일이 `docker-compose.override.yml.disabled`로 **비활성화되어 있어 실제로는 안 떠 있음** |

> `openvidu-server`/`kms`/`nginx`는 **`network_mode: host`** 를 쓴다. 즉 도커 브리지 네트워크(`edge` 등)에 물릴 수 없는 구조 — EC2 호스트의 포트에 직접 바인딩된다. 지난 답변에서 확인해 준 "`edge`는 최상위 리버스프록시·Jenkins와 공유하는 네트워크"라는 사실과 종합하면, **`edge`는 OpenVidu와는 무관하고 이 앱의 nginx ↔ Jenkins 컨테이너(웹훅 라우팅) 전용**으로 보인다.

### 5-2) 확정: OpenVidu 자체 nginx가 ssabway.site의 실제 진입점

**(작성자 확인 완료)** OpenVidu 자체 nginx가 `ssabway.site`의 실제 인터넷 진입점이며, 여기서 HTTPS를 종단한 뒤 **HTTP로 EC2 내부 nginx(이 저장소의 `deploy/nginx.conf`)로 리버스 프록시**한다. 아래 근거와 정확히 일치한다.

- `nginx` 서비스의 `WITH_APP=true` + (비활성화된) `app` 서비스가 기대하는 포트가 `SERVER_PORT=5442`
- 이 저장소의 `docker-compose.prod.yml`도 자체 nginx를 정확히 `127.0.0.1:5442`에 바인딩
- → OpenVidu 설치 시 기본 데모 앱(openvidu-call, 그래서 `.disabled`로 꺼둠) 대신 **ssabway 자체 nginx를 "WITH_APP" 슬롯에 연결**해 쓰는 구성

실제 트래픽 흐름:

```
브라우저 ──HTTPS──▶ OpenVidu nginx (host 네트워크, 80/443, Let's Encrypt, ssabway.site)
                        ├─ OpenVidu 경로(대시보드/REST API/`/recordings/**`) → 자체 처리(openvidu-server:5443, kms, coturn)
                        └─ 그 외 전부 ──HTTP──▶ 127.0.0.1:5442 (ssabway 자체 nginx, deploy/nginx.conf)
                                                    → frontend / api / signaling / ai (도커 브리지 네트워크)
```

즉 **TLS 종단은 OpenVidu nginx가 전담**하고, 이 저장소의 `deploy/nginx.conf`는 평문 HTTP만 받는다(`X-Forwarded-Proto https` 헤더를 고정으로 내려보내는 이유가 바로 이것 — 실제로는 HTTP로 들어오지만 백엔드에는 원래 HTTPS였다고 알려주는 것).

`edge` 도커 네트워크(최상위 리버스프록시·Jenkins 공유)는 이 공인 트래픽 흐름과는 별개다. OpenVidu nginx는 `network_mode: host`라 애초에 도커 브리지 네트워크에 물릴 수 없으므로, `edge`는 **이 저장소 nginx ↔ Jenkins 컨테이너 간 내부 통신 전용**(예: `/git/notifyCommit` 웹훅 라우팅)으로 정리한다.

### 5-3) 웹훅 / 녹취 설정

- `OPENVIDU_WEBHOOK=true`, `OPENVIDU_WEBHOOK_ENDPOINT=https://ssabway.site/api/v1/openvidu/webhooks` — 이 저장소 `deploy/nginx.conf`의 `/api/v1/openvidu/` → `signaling` 라우팅과 정확히 일치. 설정 맞다.
- `OPENVIDU_WEBHOOK_HEADERS=["X-OpenVidu-Webhook-Secret: {secret-key}"]` — **(작성자 확인 완료)** `{secret-key}` 자리에는 실제 키 값이 들어가 있고, 이 값이 signaling의 `OPENVIDU_WEBHOOK_SECRET`과 동일해야 `OpenViduWebhookController`(`backend/ssabway_webrtc`)를 통과한다.
- `OPENVIDU_RECORDING=true`, 저장 경로 `/opt/openvidu/recordings`(호스트 디스크), `OPENVIDU_RECORDING_PUBLIC_ACCESS=false` → `RecordingStorageService`가 `OPENVIDU_SECRET`으로 인증해 녹취 파일을 내려받은 뒤 S3로 재업로드하는 구조와 일치한다.
- `OPENVIDU_RECORDING_AUTOSTOP_TIMEOUT=120`초, `OPENVIDU_STREAMS_VIDEO_*_BANDWIDTH`(1000/300kbps) 등 대역폭 제한도 걸려 있음 — 화상 품질 이슈가 생기면 여기부터 확인.

### 5-4) 방화벽 / 보안그룹에서 열려야 하는 포트

| 포트 | 프로토콜 | 용도 |
|---|---|---|
| 80, 443 | tcp | OpenVidu 자체 nginx (Let's Encrypt 발급 + HTTPS, host 네트워크 직접 바인딩). **사실상 유일하게 외부에 열려 있어야 하는 포트** |
| 5443 | tcp | `openvidu-server` REST API. `signaling`이 이 포트로 직접 붙지 않고(아래 5-5 참고) OpenVidu 자체 nginx를 거쳐 호출하므로, 보안그룹에서 외부 공개할 필요가 없다 — 열려 있다면 닫아도 무방한 항목 |
| 3478 | tcp/udp | coturn STUN/TURN |
| 40000–57000 | udp | KMS 미디어 릴레이 (host 네트워크 직접 바인딩) — 화상 상담 실사용자 트래픽이 실제로 오가는 구간이라 반드시 열려 있어야 함 |
| 57001–65535 (기본값) | tcp/udp | coturn 릴레이(`COTURN_MIN_PORT`/`MAX_PORT`). compose의 `ports:`에는 `3478`만 게시되어 있어, 실제로 보안그룹에 열려 있는지는 서버에서 직접 확인 필요 |

### 5-5) `signaling` ↔ OpenVidu 연결 방식 (작성자 확인 완료)

`signaling`(`backend/ssabway_webrtc`)의 실제 `.env`에는 `OPENVIDU_URL=https://ssabway.site`가 설정되어 있다. 즉:

- `signaling` 컨테이너는 `openvidu-server:5443`에 직접(호스트 내부망으로) 붙는 게 아니라, **공인 도메인 `https://ssabway.site`로 나갔다가 OpenVidu 자체 nginx를 거쳐 다시 `openvidu-server`로 들어가는 경로**를 탄다(하이핀 NAT). 저장소의 `application-secret.example.yaml` 예시값(`http://localhost:4443`)은 로컬 개발 시 개발자가 직접 띄운 OpenVidu(또는 목 서버)를 가리키는 값일 뿐, 운영 값과는 무관하다.
- 이 방식이 동작하려면 EC2가 자기 자신의 퍼블릭 IP/도메인으로 나간 요청을 되받을 수 있어야 한다(대부분의 클라우드 환경에서 기본 지원되지만, 향후 다른 인프라로 옮길 때는 확인 포인트).
- `OPENVIDU_SECRET`은 `signaling`의 `OPENVIDU_SECRET` 값과 동일해야 하며, 실제 키가 채워져 있음을 확인했다(위 5-3 웹훅 시크릿과 별개의 값).

> `/opt/openvidu/.env`의 `OPENVIDU_SECRET`은 실제 운영 비밀값이라 이 문서(마크다운, git 이력에 남을 수 있음)에는 옮겨 적지 않았다. 최종 제출 시에는 이 md 문서에 값을 붙여넣기보다, `.env` 원본 파일 자체를 `exec` 폴더에 함께 첨부하는 방식을 권장한다.
